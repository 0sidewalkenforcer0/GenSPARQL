GenSPARQL · motivation

One query the KG can't answer alone — and how each approach fares

Knowledge graphs are incomplete and static: SPARQL can only return triples that already exist. Take a query that needs a fact the KG does not store, and see what every prior approach produces versus GenSPARQL.

The task

"List the Group-A players who are defenders, with their national team."

The 2026 World Cup KG stores teams, groups and squads — but no player position. Position is world knowledge an LLM has; the KG does not.

What each approach returns for this task

Pure SPARQL / KGQA
query the graph
?p ex:position ?pos . FILTER(?pos="Defender") → ∅
No position predicate exists → empty. Bounded by KG completeness.
✕
KG embeddings
TransE · ComplEx · ULTRA
(player, playsFor, ?) → 0.83, 0.71, …
Predict links among existing entities/relations; produce scores, not the value "defender", and can't be filtered or returned.
✕
RAG / LLM-over-text
retrieve → free text
"Group A defenders include Kim Min-jae, César Montes, …"
Free text: re-derives Group A itself (may be stale), not bound to variables, not linked to KG nodes, can't be joined/filtered by the engine.
✕
Text-to-SPARQL
LLM writes the query
SELECT … WHERE { ?p ex:position ?pos } → ∅
Can only compose from existing vocabulary; there is no position predicate to write against, so the generated query is still empty.
✕
LLM tool / function calls
imperative glue code
for p in players: pos = llm(p); if pos=="DEF": keep
Works, but as an ad-hoc script — not declarative, no set semantics, no query optimizer, result isn't a reusable relation.
✕
GenSPARQL (GENOP)
LLM as a first-class operator
?p ex:playsFor ?t . ?t ex:inGroup ?g . ?g rdfs:label "Group A" . GENOP("position of {?player}?", (?pos), <model>) . FILTER(?pos="Defender")
→ 41 defenders / 77 Group-A players · one declarative query · SPARQL-only: 0
KG owns the structure; the LLM fills only the missing column; the engine joins & filters — and runs the LLM only on the KG-selected bindings.
✓

GenSPARQL / KG (closed world) LLM knowledge (open world) cannot do it

Only GenSPARQL does all five: it answers the KG-missing query (coverage), binds the answer to a variable and composes it with SPARQL join/filter (composition), keeps results linked to KG nodes (entity consistency), and lets KG selectivity minimise LLM calls — 825→26, 31× (efficiency).
